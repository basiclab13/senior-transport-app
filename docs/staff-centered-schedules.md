## 기존 구조와 변경 계획

기존 화면은 선택한 날짜·오전/오후의 모든 코스를 카드로 나열했다. `BaseRoute`는 기본 코스, `RouteAssignment`는 날짜별 직원·차량·이용자 배정, `ScheduleSnapshot`은 선택한 날짜·시간대 전체 초안/확정본을 나타낸다. 이 구조와 기본 코스 데이터는 유지했다.

구현 순서는 일정 모델·검증 확장 → 관리자 목록/상세 → 직원 타임라인이다. 관리자 단계에서 정적 분석과 전체 테스트를 실행한 후 직원 화면을 구현했다. Firebase 초기화, 로그인, 사용자 문서 검증, admin/staff 분기 및 Firestore Rules는 변경하지 않았다.

## 화면 구성

| 파일 | 책임 |
|---|---|
| `lib/screens/schedule_screen.dart` | 인증된 사용자의 공통 프레임, 날짜/오전·오후/오늘 선택, 로그아웃, 전체 검증·확정 |
| `lib/screens/admin_schedule_view.dart` | 직원 이름 검색, 근무 가능 여부/배정 필터, 선택 직원 상세 및 배정 편집 |
| `lib/screens/staff_schedule_view.dart` | 본인 확정 일정의 차량·예상 운행 시간·방문 타임라인 조회 |
| `lib/widgets/route_timeline.dart` | 방문 순서, 예상 시각, 가상 이름·위치·주의사항 표시 |
| `lib/widgets/estimated_time_dialog.dart` | 관리자 예상 시각 입력·수정 및 HH:mm 형식 검사 |
| `lib/screens/attendance_screen.dart` | 사진 인증이 아직 미제공임을 설명하는 안내 화면 |

900px 이상에서는 직원 목록과 선택 직원 상세를 좌우로 표시한다. 더 좁은 화면에서는 목록만 표시하고 직원 선택 시 상세로 전환한다. `직원 목록으로` 버튼으로 돌아오며 검색 조건을 유지한다. 목록은 `ListView.builder`로 필요한 직원 행만 생성한다. 전체 직원의 상세 카드를 나열하지 않는다.

관리자는 직원 선택 후 기존 코스명과 차량을 확인하고 담당 직원·차량, 이용자, 방문 순서 및 예상 시각을 수정한다. 미배정 직원은 `기존 코스 배정`에서 코스 전체를 인계받을 수 있다. 이용자 재배정 대상은 이미 코스가 있는 다른 직원이며, 미배정 직원에게는 먼저 기존 코스를 배정한다. 새 기본 코스를 자동 생성하지 않는다.

`이용자 추가·복귀·재배정`에서는 해당 시간대 기본 코스의 기존 이용자를 이름으로 검색한다. 다른 직원에게 배정된 이용자는 기존 배정에서 제거 후 선택 코스에 추가한다. 결석/제외 이용자는 선택한 코스에 복귀시킨다. 새로운 이용자 마스터 등록 기능은 이 화면의 범위에 포함하지 않았다.

직원 화면은 `users/{uid}.staffId`로 연결된 본인의 확정 일정만 사용한다. 날짜, 오전·오후, 차량, 관리자가 입력한 예상 운행 구간/분수, 이용자 방문 순서·예상 시각·위치를 표시한다. 다른 직원 선택이나 편집 컨트롤은 제공하지 않는다. `오늘`을 누르면 실행 중인 브라우저의 현재 날짜로 이동한다.

## 모델 확장

| 데이터 | 필드 | 의미 |
|---|---|---|
| `RouteAssignment` | `estimatedVisitMinutes: Map<String, int>` | 이용자 ID별 예상 방문 시각. 해당 날짜의 자정부터 분 단위 |
| `RouteAssignment` | `startMinute`, `endMinute` | 선택적 관리자 입력 예상 출발·종료 시각. 둘을 함께 입력/삭제 |
| `ScheduleSnapshot` | `excludedIds: Set<String>` | 선택한 날짜·시간대에서 송영 제외된 이용자. 결석 `absentIds`와 구분 |

기본 코스에는 예상 시각을 추가하지 않았다. 시각과 제외 정보는 날짜·시간대별 초안과 확정본에만 포함된다. 모든 컬렉션은 불변 복사한다. 직원·차량은 코스별 단일 ID를 유지한다.

방문 시각은 자동 계산하지 않는다. 미입력은 그대로 표시하고, 실제 운행 시각과 다를 수 있음을 양쪽 화면에 안내한다. 재배정·제외·결석 시 해당 이용자의 이전 예상 시각을 제거한다. 순서 변경 시 입력 시각은 보존하고 시각 역전이 생기면 검증 오류로 표시하여 관리자가 수정하도록 한다.

## 전체 변경 검증과 확정

직원 상세에서는 선택한 직원만 편집하지만, 검증과 확정의 단위는 **선택 날짜·시간대 전체 직원의 일정**이다. 검색·필터로 숨겨진 직원도 검증 대상이다. 확정 전 대화상자에 직원, 코스, 차량, 방문 순서 및 예상 시각을 함께 표시한다. 관리자가 확인한 동일한 스냅샷만 확정한다. 기존 확정본은 재확정 전까지 유지한다.

차단하는 오류:

- 근무 불가 직원 배정, 동일 시간대 직원·차량 중복 배정
- 차량 정원 초과, 이용자 중복·누락, 잘못된 참조
- 결석/제외 이용자 배정 및 결석·제외 상태의 중복
- 잘못된 예상 시각, 출발/종료 역전, 방문 순서와 시각 충돌, 운행 범위 밖 방문 시각
- 배정에서 제거된 이용자의 예상 시각이 남아 있는 경우

예상 시각 미입력은 별도 안내이며 확정 자체를 막지 않는다. 원래 시제품과 같이 같은 시간대 코스는 동시에 운행하는 것으로 검증하므로, 같은 직원·차량의 여러 코스 순차 운행은 지원하지 않는다. 차량 정원은 현재 이용자 수 기준의 시연 규칙이다.

## 현재 한계와 남은 작업

- **일정은 메모리에만 저장된다.** 새로고침, 로그아웃, 권한 화면 재생성 시 초기화되며 Firebase로 영구 저장·계정 간 공유되지 않는다. 직원 화면을 확인하기 위해 임의의 확정 일정을 앱 실행 시 생성하지 않는다. 실제 직원 로그인에서는 서버 일정 조회가 아직 없어 빈 일정이 표시된다.
- `ScheduleController.initialConfirmed`는 검증된 확정 스냅샷을 전달받는 로컬 경계이며 현재 화면 테스트에서 사용한다. Firebase 저장소 연결을 의미하지 않는다. 직원 타임라인 테스트는 이 경계로 가상 확정 데이터를 전달해 검증한다.
- 직원·이용자·차량 목록은 기존 가상 데이터다. 수십 명을 실제로 저장·조회하는 직원 마스터, Firestore 검색/페이지 나누기는 별도 작업이다. 기존 직원 ID s1/s2/s3 인증 매핑을 유지했다.
- 사진 인증 버튼은 **안내 화면으로 이동**한다. 촬영·업로드·출퇴근 기록 생성 기능은 구현하지 않았고 기록 완료로 표시하지 않는다. 후속 작업에서 Storage 권한 규칙과 신뢰할 수 있는 기록 생성 API를 연결해야 한다.
- Firestore Rules는 이번 변경으로 완화하지 않았다. 일정 서버 접근은 기존처럼 차단 상태이며, 향후 저장 구현 시 서버 권한 검증과 배포된 Rules 검증이 필요하다. 클라이언트 UI만으로 실제 운영 데이터의 권한 보호가 완료되지는 않는다.

## 검증

관리자 단계의 `flutter analyze`와 31개 테스트를 통과했다. 이후 직원 타임라인·날짜/시간대 전환·사진 안내 이동, 권한 변경/로그아웃 시 열린 화면 폐기, PC/모바일 목록 분리, 작은 모바일(320×568), 재배정 후 여러 직원 변경 일괄 확정 테스트를 추가했다.

최종 `flutter analyze`는 No issues found, `flutter test`는 37개 모두 통과했으며 `flutter build web`도 성공했다. 실제 Firebase 계정/운영 규칙 검증과 일정 서버 연동 검증은 이번 로컬 UI 테스트의 범위에 포함되지 않는다.
