# Requirements: 노인주간보호센터 송영 업무 관리 앱

## 1. 문서 개요

### 1.1. 목적

본 문서는 노인주간보호센터 송영 업무 관리 애플리케이션의 기능 요구사항과 비기능 요구사항을 정의한다.

개발 과정에서 기능의 구현 범위와 완료 여부를 판단하는 기준으로 사용한다.

프로젝트의 배경과 문제 상황은 `project-overview.md`를 참고한다.

### 1.2. 개발 목표

다음 세 가지 핵심 기능을 구현한다.

1. 직원별 송영 일정 조회
2. AI 기반 송영 일정 조정 지원
3. 출퇴근 기록 자동 작성

### 1.3. 개발 환경

- 프론트엔드: Flutter
- 대상 플랫폼: Web / PWA
- 사용자 인증: Firebase Authentication
- 데이터베이스: Cloud Firestore
- 사진 저장: Firebase Cloud Storage
- 서버 기능: Firebase Cloud Functions
- AI 기능: 외부 LLM API 활용
- 버전 관리: Git / GitHub
- AI 개발 보조: Codex

기술 스택은 구현 과정에서 필요에 따라 변경할 수 있다.

## 2. 사용자 역할 및 권한

시스템은 두 가지 사용자 역할을 지원한다.

### 2.1. 관리자(Admin)

송영 일정을 수립하고 관리하는 담당자이다.

**사용 가능 기능**

- 전체 직원의 송영 일정 조회
- 송영 일정 생성 및 수정
- 직원과 차량 배정 변경
- 이용자 결석 처리
- AI 일정 조정안 요청 및 확인
- AI 조정안 승인 또는 거절
- 직원별 출퇴근 기록 조회

### 2.2. 직원(Staff)

실제 송영 업무를 수행하는 사용자이다.

**사용 가능 기능**

- 본인의 송영 일정 조회
- 담당 이용자 및 방문 순서 조회
- 송영 시작 및 종료 사진 인증
- 본인의 출퇴근 기록 조회

직원은 다른 직원의 일정이나 출퇴근 기록을 임의로 수정할 수 없다.

### 2.3. 공통 요구사항

- 사용자는 로그인 후 시스템을 이용할 수 있어야 한다.
- 로그인한 사용자의 역할에 따라 사용 가능한 화면과 기능이 달라야 한다.
- 화면에서 기능을 숨기는 것뿐 아니라 서버와 데이터베이스 수준에서도 접근 권한을 제한해야 한다.
- 로그아웃 기능을 제공해야 한다.

## 3. 기능 요구사항

### FR-01. 사용자 로그인 및 권한 관리

**목적:** 사용자별로 적절한 기능과 정보에 접근하도록 한다.

**세부 요구사항**

- FR-01-01: 사용자는 이메일과 비밀번호로 로그인할 수 있어야 한다.
- FR-01-02: 로그인 성공 시 사용자 역할을 확인해야 한다.
- FR-01-03: 관리자는 관리자용 화면으로 이동해야 한다.
- FR-01-04: 직원은 직원용 화면으로 이동해야 한다.
- FR-01-05: 인증되지 않은 사용자는 송영 정보에 접근할 수 없어야 한다.
- FR-01-06: 사용자는 로그아웃할 수 있어야 한다.

**완료 조건**

- 관리자와 직원 계정으로 각각 로그인할 수 있다.
- 직원 계정으로 관리자 전용 데이터와 수정 기능에 접근할 수 없다.
- 로그아웃 이후 보호된 화면에 접근할 수 없다.

### FR-02. 직원별 송영 일정 조회

직원 중심 관리자 화면과 직원 타임라인의 현재 설계·구현 범위는 [staff-centered-schedules.md](staff-centered-schedules.md)를 참고한다. 예상 시각은 관리자 입력값이며 실제 운행 시각을 보장하지 않는다.

Firestore 영구 저장·직원별 실시간 공유·서버 권한 검증과 로컬 Emulator 실행은 [firestore-schedules.md](firestore-schedules.md)에 정리한다.

**목적:** 직원이 자신의 최신 송영 일정을 간편하게 확인하도록 한다.

**세부 요구사항**

- FR-02-01: 직원은 로그인 후 자신의 오늘 송영 일정을 확인할 수 있어야 한다.
- FR-02-02: 다른 날짜를 선택하여 일정을 조회할 수 있어야 한다.
- FR-02-03: 오전 송영과 오후 송영을 구분하여 표시해야 한다.
- FR-02-04: 담당 코스와 배정된 차량 정보를 확인할 수 있어야 한다.
- FR-02-05: 해당 코스의 이용자 목록과 방문 순서를 확인할 수 있어야 한다.
- FR-02-06: 관리자가 일정을 변경하고 확정하면 직원은 최신 확정 일정을 확인할 수 있어야 한다.
- FR-02-07: 일정이 없는 경우 별도의 안내 메시지를 표시해야 한다.

**완료 조건**

- 직원 A는 자신의 일정만 조회할 수 있다.
- 오전·오후 송영 일정이 구분되어 표시된다.
- 관리자가 확정한 변경사항이 직원 화면에 반영된다.

### FR-03. 송영 일정 관리 및 수동 조정

**목적:** 관리자가 기존 송영 계획을 바탕으로 날짜별 일정을 관리하도록 한다.

**세부 요구사항**

- FR-03-01: 관리자는 날짜별 전체 송영 일정을 조회할 수 있어야 한다.
- FR-03-02: 기존 송영 코스를 바탕으로 특정 날짜의 일정을 생성할 수 있어야 한다.
- FR-03-03: 이용자의 결석 여부를 해당 날짜의 일정에 반영할 수 있어야 한다.
- FR-03-04: 직원의 휴무 또는 근무 불가 상황을 반영할 수 있어야 한다.
- FR-03-05: 코스에 배정된 직원과 차량을 변경할 수 있어야 한다.
- FR-03-06: 코스에 포함된 이용자와 방문 순서를 수정할 수 있어야 한다.
- FR-03-07: 변경사항을 저장하기 전에 확인할 수 있어야 한다.
- FR-03-08: 관리자는 수정된 일정을 확정할 수 있어야 한다.
- FR-03-09: 확정된 일정은 해당 직원의 일정 조회 화면에 반영되어야 한다.
- FR-03-10: 특정 날짜의 일정 변경이 기본 송영 코스에 자동으로 영향을 주어서는 안 된다.

**완료 조건**

- 특정 날짜의 이용자 한 명을 결석 처리할 수 있다.
- 직원 배정과 방문 순서를 수정할 수 있다.
- 변경사항을 확정한 뒤 직원 화면에서 확인할 수 있다.
- 다음 날짜의 기본 송영 코스는 변경되지 않는다.

### FR-04. AI 기반 송영 일정 조정 지원

**목적:** 관리자가 송영 일정을 조정할 때 AI가 가능한 조정안을 추천하도록 한다.

**기본 원칙**

- AI는 일정 조정을 지원하는 역할만 수행한다.
- AI가 실제 송영 일정을 직접 확정하거나 저장해서는 안 된다.
- 관리자가 조정안을 검토하고 승인해야 적용된다.
- 필수 제약조건은 AI 응답과 별도로 프로그램에서 검증한다.

**세부 요구사항**

- FR-04-01: 관리자는 특정 날짜의 일정에 대해 AI 조정안을 요청할 수 있어야 한다.
- FR-04-02: AI는 기존 일정과 변경사항을 입력받아야 한다.
- FR-04-03: AI는 이용자 결석, 직원 근무 변경 등의 상황을 고려하여 해당 날짜와 시간대의 전체 송영 일정을 분석하고, 필요한 경우 코스 간 이용자 재배정 및 방문 순서 변경을 포함한 조정안을 제안해야 한다.
- FR-04-04: AI는 가능한 한 기존 송영 코스를 유지하는 방향으로 조정안을 제안해야 한다.
- FR-04-05: AI 조정안에는 변경 대상과 변경 이유가 포함되어야 한다.
- FR-04-06: 시스템은 AI 조정안이 필수 제약조건을 위반하는지 검증해야 한다.
- FR-04-07: 검증되지 않았거나 조건을 위반한 조정안은 확정할 수 없어야 한다.
- FR-04-08: 관리자는 제안된 조정안을 확인하고 필요하면 수동으로 수정할 수 있어야 한다.
- FR-04-09: 관리자는 조정안을 승인하거나 거절할 수 있어야 한다.
- FR-04-10: AI가 유효한 조정안을 생성하지 못한 경우 오류 또는 조정 불가 사유를 표시해야 한다.
- FR-04-11: AI API 호출은 서버에서 수행하며 API 키를 클라이언트에 노출하지 않아야 한다.

**AI 입력 데이터**

- 조정 대상 날짜
- 기존 송영 일정
- 이용자의 결석 정보
- 직원의 근무 가능 여부
- 코스별 직원 및 차량 배정
- 이용자 방문 순서
- 적용 가능한 제약조건

**AI 출력 데이터**

- 변경이 필요한 코스
- 변경 전후의 직원 배정
- 변경 전후의 이용자 구성 및 방문 순서
- 조정 이유
- 해결되지 않은 문제 또는 추가 확인이 필요한 사항

AI 출력은 프로그램이 해석하고 검증할 수 있는 구조화된 데이터 형식으로 정의한다.

**필수 검증 항목**

- 근무할 수 없는 직원이 배정되지 않아야 한다.
- 한 직원이 동일 시간대에 서로 충돌하는 업무를 배정받지 않아야 한다.
- 차량 정원을 초과하지 않아야 한다.
- 결석한 이용자가 해당 날짜의 송영 대상에 포함되지 않아야 한다.
- 하나의 이용자가 같은 송영 시간대에 중복 배정되지 않아야 한다.
- 존재하지 않는 직원, 차량 또는 이용자를 참조해서는 안 된다.

실제 시간 충돌 판단 기준과 차량 탑승 인원 산정 방식은 추가 업무조사를 통해 확정한다.

**완료 조건**

- 관리자가 결석 또는 직원 휴무 상황에 대해 AI 추천을 요청할 수 있다.
- AI가 조정안과 변경 이유를 제시한다.
- 제약조건을 위반하는 조정안은 적용되지 않는다.
- 관리자가 승인한 경우에만 실제 일정이 변경된다.
- AI 추천이 실패해도 수동 일정 조정 기능은 정상 작동한다.

### FR-05. 출퇴근 사진 인증 및 기록 자동 작성

**목적:** 송영 시작과 종료 인증을 바탕으로 직원 출퇴근 기록을 자동 생성한다.

**세부 요구사항**

- FR-05-01: 직원은 자신의 송영 일정에서 출근 인증 기능을 사용할 수 있어야 한다.
- FR-05-02: 직원은 첫 송영지에서 사진을 촬영하거나 첨부하여 출근을 인증할 수 있어야 한다.
- FR-05-03: 시스템은 인증한 직원, 날짜, 인증 시각과 사진을 기록해야 한다.
- FR-05-04: 직원은 마지막 송영지에서 사진을 촬영하거나 첨부하여 퇴근을 인증할 수 있어야 한다.
- FR-05-05: 시스템은 출근과 퇴근 인증을 바탕으로 출퇴근 기록을 자동 생성하거나 갱신해야 한다.
- FR-05-06: 직원은 자신의 출퇴근 인증 상태를 확인할 수 있어야 한다.
- FR-05-07: 관리자는 직원별 출퇴근 기록을 조회할 수 있어야 한다.
- FR-05-08: 사진 업로드에 실패하면 실패 사실을 안내하고 재시도할 수 있어야 한다.
- FR-05-09: 동일한 직원의 동일 날짜 인증이 중복 기록되지 않도록 해야 한다.
- FR-05-10: 기록에는 인증 시각과 인증 유형(출근·퇴근)을 구분하여 저장해야 한다.

**완료 조건**

- 직원이 출근 사진을 제출하면 출근 인증 시각이 기록된다.
- 퇴근 사진을 제출하면 해당 날짜의 퇴근 인증 시각이 기록된다.
- 담당자가 출퇴근 기록을 조회할 수 있다.
- 동일한 인증을 반복하더라도 중복 출퇴근 기록이 생성되지 않는다.

사진 인증만으로 실제 송영지 도착 여부가 자동 검증되는 것은 아니다. GPS 기반 위치 확인은 초기 개발 범위에서 제외한다.

## 4. 주요 데이터 요구사항

다음 데이터를 관리할 수 있어야 한다.

| 데이터 | 주요 항목 |
|---|---|
| 직원 | 직원 ID, 이름, 사용자 역할, 근무 가능 여부 |
| 이용자 | 이용자 ID, 가상 이름, 주소 또는 위치, 송영 시 주의사항 |
| 차량 | 차량 ID, 차량명, 정원 |
| 기본 송영 코스 | 코스 ID, 오전·오후 구분, 기본 방문 순서 |
| 날짜별 송영 일정 | 날짜, 코스, 담당 직원, 차량, 이용자 목록, 방문 순서, 확정 상태 |
| 출퇴근 기록 | 직원 ID, 날짜, 출근·퇴근 인증 시각, 사진 저장 경로 |
| AI 조정안 | 대상 일정, 추천 변경사항, 변경 이유, 검증 결과, 승인 상태 |

**데이터 관리 원칙**

- 직원, 이용자, 차량 등의 데이터는 고유한 ID로 참조한다.
- 기본 송영 코스와 날짜별 송영 일정은 구분하여 관리한다.
- 날짜별 일정은 오전과 오후를 구분한다.
- AI 추천 결과와 실제 확정 일정은 구분한다.
- 출퇴근 기록은 인증한 사용자와 연결되어야 한다.
- 데이터베이스의 세부 컬렉션 및 필드 구조는 별도로 설계한다.

## 5. 화면 요구사항

최소한 다음 화면을 제공한다.

| 화면 | 주요 기능 | 접근 권한 |
|---|---|---|
| 로그인 | 사용자 로그인 | 공통 |
| 직원 홈 | 오늘의 송영 일정 확인 | 직원 |
| 송영 일정 상세 | 코스, 차량, 이용자, 방문 순서 확인 | 직원·관리자 |
| 관리자 홈 | 날짜별 전체 송영 일정 확인 | 관리자 |
| 송영 일정 편집 | 결석 처리, 직원·차량 변경, 순서 수정 | 관리자 |
| AI 조정안 확인 | AI 추천 및 검증 결과 확인, 승인·거절 | 관리자 |
| 출퇴근 인증 | 출근·퇴근 사진 인증 | 직원 |
| 출퇴근 기록 조회 | 직원별 인증 기록 확인 | 관리자·본인 |

모바일 화면을 우선 설계하며, 관리자는 PC에서도 편리하게 일정을 확인하고 수정할 수 있어야 한다.

## 6. 비기능 요구사항

### NFR-01. 사용성

- 스마트폰 화면에서 주요 기능을 쉽게 사용할 수 있어야 한다.
- 직원이 로그인한 뒤 자신의 오늘 일정을 빠르게 확인할 수 있어야 한다.
- 일정 조정과 출퇴근 인증 과정은 가능한 한 적은 단계로 구성한다.
- 로딩, 저장 성공, 오류 발생 상태를 사용자에게 명확히 표시한다.

### NFR-02. 데이터 일관성

- 여러 사용자가 동일한 일정에 접근하더라도 확정된 최신 데이터를 조회할 수 있어야 한다.
- 관리자 간 동시 수정이 발생한 경우 기존 변경사항이 무조건 덮어써지지 않도록 처리해야 한다.
- 일정 저장과 확정 과정에서 데이터의 일관성을 유지해야 한다.

### NFR-03. 보안 및 개인정보 보호

- 사용자 인증 및 역할별 접근 권한을 적용한다.
- 직원은 허용된 정보에만 접근할 수 있어야 한다.
- 사진 파일은 인증되지 않은 사용자가 임의로 조회할 수 없어야 한다.
- API 키와 서버 비밀정보는 앱 코드 및 GitHub 저장소에 노출하지 않는다.
- 개발 및 테스트에는 가상 데이터를 사용한다.
- 사용자 입력값과 AI 출력값은 서버에서 검증한다.

### NFR-04. 안정성

- AI API가 응답하지 않아도 기본적인 송영 일정 조회와 수동 수정 기능을 사용할 수 있어야 한다.
- 네트워크 오류나 사진 업로드 실패 시 사용자에게 안내해야 한다.
- 잘못된 일정 데이터가 확정되지 않도록 검증해야 한다.

### NFR-05. 유지보수성

- 화면, 데이터 처리, 비즈니스 로직을 가능한 한 분리한다.
- 기능별로 코드를 모듈화한다.
- 공통 데이터 모델과 명명 규칙을 통일한다.
- 주요 비즈니스 로직에는 자동화 테스트를 작성한다.
- Git 브랜치와 Pull Request를 활용하여 변경사항을 관리한다.

## 9. 추가 확인이 필요한 업무 규칙

다음 사항은 현재 확정하지 않는다.

### 송영 코스 및 직원 배정

- 한 코스에 운전원 외 다른 직원도 함께 배정되는가?
- 한 직원이 같은 시간대에 여러 코스를 담당할 수 있는가?
- 한 차량에 배정 가능한 직원 수는 어떻게 결정되는가?
- 직원이 휴무일 때 대체 직원을 선정하는 기준은 무엇인가?

### 이용자 및 방문 순서

- 기본 송영 코스는 어떤 주기로 변경되는가?
- 결석자가 발생하면 방문 순서도 변경하는가?
- 어르신별 탑승·하차 지원에 필요한 별도 제약조건이 있는가?
- 차량 정원은 직원의 탑승 인원을 포함하여 판단하는가?

### 출퇴근 인증

- 첫 송영지와 마지막 송영지는 어떤 기준으로 결정되는가?
- 출퇴근 사진에 반드시 포함되어야 하는 정보가 있는가?
- 사진 인증을 누락한 경우 누가 어떻게 수정하는가?
- 같은 날짜에 오전·오후 인증을 별도로 관리해야 하는가?
- 사진의 보관 기간은 어떻게 정하는가?

확정되지 않은 업무 규칙을 Codex나 AI가 임의로 실제 운영 규칙으로 가정해서는 안 된다.

## 10. 프로젝트 완료 기준

다음 시나리오가 정상적으로 작동하면 MVP가 구현된 것으로 판단한다.

**시나리오 A: 직원별 일정 조회**

1. 직원 A가 로그인한다.
2. 오늘의 오전·오후 송영 일정을 확인한다.
3. 자신에게 배정된 코스와 방문 순서를 확인한다.

**시나리오 B: 일정 변경 및 공유**

1. 관리자가 특정 날짜의 송영 일정을 조회한다.
2. 이용자 한 명을 결석 처리한다.
3. 필요한 경우 직원 배정 또는 방문 순서를 수정한다.
4. 변경된 일정을 확정한다.
5. 직원이 로그인하여 변경된 최신 일정을 확인한다.

**시나리오 C: AI 일정 조정**

1. 관리자가 직원 휴무 등 변경사항을 등록한다.
2. AI 일정 조정안을 요청한다.
3. 시스템이 제약조건을 검증한 조정안을 표시한다.
4. 관리자가 조정안을 검토하고 승인한다.
5. 확정된 일정이 해당 직원에게 표시된다.

**시나리오 D: 출퇴근 기록**

1. 직원이 출근 인증 사진을 제출한다.
2. 시스템이 직원과 출근 인증 시각을 기록한다.
3. 직원이 퇴근 인증 사진을 제출한다.
4. 시스템이 퇴근 인증 시각을 기록한다.
5. 관리자가 해당 직원의 출퇴근 기록을 조회한다.
