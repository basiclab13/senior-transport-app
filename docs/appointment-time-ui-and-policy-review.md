# 오전 약속 시간·오후 방문 순서: UI 적용과 정책 검토

> 이전 UI 적용·정책 검토 기록입니다. 이후 승인된 [방문 시간 단순화](appointment-time-simplification.md)가 현재 구현입니다. 약속 확인 필드 추가·필수화 제안은 채택하지 않았으며 B-1/B-2와 시간 순서에 따른 확정 차단은 제거했습니다.

2026-11-14. 이번에는 UI 표시/안내만 구현했다. 시간 저장 구조, controller의 계산·B-2·확정 검증, Cloud Functions/Rules/인증, 운영 Firestore는 변경하지 않았다. 실제 Firebase 조회·배포·Gemini 호출도 하지 않았다.

## 현재 데이터와 검증에서 확인한 사실

| 현재 필드/기능 | 실제 의미 |
| --- | --- |
| routes[].estimatedVisitMinutes | 이용자별 당일 분 단위 시각. 오전/오후에 같은 구조 사용 |
| estimatedVisitSources.manual | 직접 입력 방식. **어르신과 약속 확인을 완료했다는 증거는 아님** |
| estimatedVisitSources.fixedInterval | 간격 계산 결과. 약속 시간으로 자동 확정할 수 없음 |
| 출처 없음 | 기존 데이터. 덮어쓰기 방지는 수동으로 취급하지만 실제 약속 여부는 모름 |
| startMinute/endMinute | 운행 참고 구간. 둘 다 없음은 허용, 하나만 있음/역전은 오류 |
| B-1 | 첫 시각+간격으로 계산, 미리보기·명시적 적용, 수동/기존값 덮어쓰기는 별도 확인 |
| B-2 | 순서·인원·담당 변경 시 재검토. 기존 시각 유지도 충돌 검사. 현재 오후/시간 없음도 재검토 대상으로 표시 |

controller.validate와 functions/validation.js는 둘 다 시각 미입력 자체를 허용한다. 입력값의 0~1439 범위, 배정 대상/출처, 방문 순서상 증가/중복, 운행 구간과의 충돌은 검사한다. 서버는 source를 manual/fixedInterval만 허용하며, 약속 여부를 기록하는 별도 필드가 없다.

따라서 현재 값을 일괄 약속 완료로 변환하거나, 기존 오후 시각 검사를 UI에서만 우회하면 안 된다.

## 이번 UI 구현

- AppBar에 화면 제목을 한 번만 표시하고 송영도우미는 작은 브랜드 캡션으로 유지. 본문의 중복 제목/설명, 요청한 실제 운행과 다를 수 있다는 일반 문장을 삭제했다.
- 직원 화면은 이름·코스·차량·방문 순서·사진 상태를 유지. 운행 참고 구간이 비어 있으면 불필요한 미입력 문구를 표시하지 않는다.
- 오전 타임라인은 다음처럼 구분한다.

| 데이터 | 화면 |
| --- | --- |
| 직접 입력 | 약속 시간 **입력값** 08:10 · 직접 입력 |
| 자동 계산만 있음 | 약속 시간 미입력 · 계산 참고 08:20 |
| 기존 값, 출처 없음 | 기존 입력 08:30 · 약속 여부 확인 |
| 시각 없음 | 약속 시간 미입력 |

입력값이라고 표시하는 이유는 기존 manual 값도 과거에는 예상 시각으로 입력됐을 수 있기 때문이다. 입력 방식을 실무 약속 확인 상태로 자동 승격하지 않는다. 실제 약속 성립/확인 여부는 아래 후속 정책으로 별도 다뤄야 한다.

- 오전 직접 수정창은 약속 시간 입력으로 안내하고 실제 약속 시간을 확인하도록 한다. 저장은 기존 필드/source=manual 방식 그대로다.
- 자동 계산 화면은 **참고 시간이며 약속 시간이 아님**을 명시한다. 기존 수동 보호·출처 보존·명시적 덮어쓰기 확인을 유지한다.
- 오후는 기본 타임라인에서 시각/시간 미입력 안내를 숨긴다. 저장된 값은 삭제하지 않고 방문 항목을 펼치면 **기존 저장 시각 + 입력 방식**으로 확인한다. 관리자 계산 기능은 추가 설정에 선택 기능으로 남긴다.
- 오후의 단순 미입력 안내는 adminTimeNotices 표시 함수에서 제외한다. controller.planningWarnings와 확인/서버 검증은 바꾸지 않았다. 실제 차단 오류와 B-2 미완료는 숨기지 않는다.
- 날짜·오전/오후 자동 선택·수동 선택 유지, 사진 캐시·조회, AI 검토 후 적용·확정은 유지했다. 새 Firebase 조회는 추가하지 않았다.

## 약속 시간 부재로 확정을 막을 것인가

**이번에는 막지 않는다.** 기존 앱/서버에 없는 차단 규칙을 문구 변경과 함께 켜면, 기존 정상 확정 일정과 가상 fixture가 예고 없이 실패한다. 출처가 manual인지와 약속을 확인했는지도 다르다.

권장: 현재는 오전 입력·확인 안내를 유지하고, 실제 센터가 오전 송영 대상 모두의 약속 확인을 필수로 하기로 결정하면 다음 단계에서 서버와 함께 도입한다. 결석·제외 대상은 필수 검사에서 제외한다. 오전/오후에 동일한 필수 규칙을 적용하지 않는다.

## 후속 변경안 — 아직 구현하지 않음

### 최소 데이터 확장

estimatedVisitSources를 약속 여부로 재해석하거나 새 enum 값을 몰래 추가하지 않는다. 예를 들어 선택 필드 **appointmentConfirmedIds**를 코스에 추가해 직접 입력 시간과 별도로 관리할 수 있다(제안 이름이며 현재 필드 아님).

- 확인 ID는 해당 코스의 실제 이용자이고 직접 입력 시각이 있어야 한다.
- 자동 계산 적용·시각 수정은 기존 확인 상태를 해제하고 명시적 약속 재확인을 요구한다. 실제 약속이 유지된 단순 담당 인계/조회로 임의 해제하지 않는다.
- 기존 문서에 필드가 없으면 미확인으로 읽되 자동 수정하지 않는다. 운영자가 기존 시각의 실무 의미를 검토한다.
- 약속 시간을 유지하면서 별도 참고 계산값도 저장해야 한다면 두 맵 분리가 추가로 필요하다. 현재 한 맵/source만으로 둘을 동시에 저장할 수 없다.

### 오전 검증

필수화 승인 후 미확인/미입력 오전 대상 차단을 controller와 confirmSchedule 양쪽에 같은 기준으로 추가한다. 입력 범위/정원/중복/결근/동시 수정 검증은 유지한다. 기존 데이터를 확인하기 전에는 정책을 활성화하지 않는 호환 단계가 필요하다.

수정 범위: transport.dart, schedule_codec.dart, schedule_controller.dart, calculator/검토 UI, Functions validation.js/schedule-service.js/existing-schedule.js 및 직원 projection. 선택 필드여도 기존 서버의 허용 필드 검사에 걸리므로 **새 UI만 먼저 배포하지 않는다.** 구버전 클라이언트가 새 확인 정보를 누락·삭제하지 못하는 처리도 필요하다.

### 오후 순서 중심 확정

최소 후속 단계는 **시간 기록이 전혀 없는 오후 코스**의 순서/인원 변경에 B-2 시간 승인을 요구하지 않는 것이다. 기존 서버는 빈 시각을 허용하므로 별도 서버 완화 없이 controller의 재검토 조건을 조정할 수 있다. 그러나 이는 현재 확정 조건을 바꾸므로 이번에는 하지 않았다.

시간 기록이 있는 오후 코스는 현재 순서를 바꾸면 기존 시각 역전으로 확정이 막힐 수 있다. 이를 완전히 순서 중심으로 바꾸려면 다음을 함께 승인해야 한다.

1. 기존 시각을 어떤 기록으로 보존할지 결정(현재 필드 유지/별도 보존 필드).
2. 오후 B-2와 서버의 순서·구간 시각 검사를 비차단 안내로 바꿀지 결정.
3. 입력 형식·이용자 연결·출처 검사와 정원/근무/중복 검증은 유지.
4. 기존 확정 문서를 자동 삭제/재확정하지 않고 구버전 호환 검증.

**현재 UI에서 오후 미입력 안내가 사라진 것과, 오후 시각 검증이 제거된 것은 다르다.** 기존 오후 값이나 B-2가 있는 경우 이번 버전도 기존 검증에 따라 확정을 막는다.

## AI 검토

현재 Gemini에는 직원/코스/이용자 임시 ID, 정원, 가용성, 선택적 가상 좌표가 전달되며 방문 시각/출처는 추천 수정 대상이 아니다. 서버 assembleSuggestion과 Flutter 적용은 이용자 ID를 기준으로 기존 시각/출처를 보존한다. 차/결석 상태/확정 일정의 직접 변경도 허용하지 않는다.

다만 서버의 AI 추천 단계는 구조 검증과 시각 재검토 안내를 분리한다. 따라서 기존 시각과 충돌하는 순서를 추천할 수 있고, 현재는 B-2/최종 확정 단계에서 해결한다. **오전 약속을 반드시 지켜야 하는 최적화가 구현됐다고 볼 수 없다.**

약속 정책 도입 시에는 확인된 오전 약속의 순서를 추천 단계에서 서버가 검사하고, 위반 추천은 자동 계산으로 약속을 바꾸게 유도하지 않고 거절/재검토해야 한다. 필요하면 약속 제약을 임시 ID로 비식별화해 AI에 전달한다. 프롬프트만으로 보장하지 않는다. 이때 suggestion-service.js/ai-privacy.js/gemini-schedule.js와 관련 테스트 변경이 필요하다. 이번에는 기존 AI 입력/프롬프트/검증·키·한도를 변경하지 않았다.
