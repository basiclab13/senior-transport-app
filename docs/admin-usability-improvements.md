# 관리자 사용성 보완: 이름 정렬·재배정·확정 변경 요약

operations-scale-validation.md의 권고 중 세 가지에만 대응한다. 기존 좌우 직원/상세 레이아웃과 모바일 전환을 유지한다. Auth, Firestore schema/저장소, confirmSchedule, Security Rules, 서버 검증, expectedVersion 및 requestId 처리에는 변경이 없다. 실제 Firebase 데이터 수정이나 배포를 수행하지 않는다.

## 직원 이름 정렬

직원 목록, 전체 배정 현황, 담당 직원 드롭다운 및 재배정 대상은 직원 이름으로 정렬한다. 숫자 구간은 문자열 순서가 아닌 자연 순서로 비교하므로 직원 1, 직원 2, 직원 10 순이다. 큰 숫자도 정수 변환 범위에 의존하지 않는다. 같은 이름은 직원 ID로 일관되게 구분한다. 정렬은 복사한 UI 목록에만 적용하며 원본 catalog와 staffId·사용자 연결·일정 payload 순서를 바꾸지 않는다. 기존 선택은 직원 ID로 유지한다.

공통 함수: lib/utils/staff_sort.dart.

## 이용자 재배정

방문 항목의 `재배정 →`를 누르면 긴 팝업 메뉴 대신 검색 가능한 선택 창을 연다.

- 직원 이름 검색과 `근무 가능만`, `정원 여유만` 필터를 함께 사용한다. 필터 기본값은 전체다.
- 직원 이름·담당 코스·직원 총 배정 인원·차량·현재 인원/정원·이동 후 인원·근무 여부를 표시한다.
- 정원 초과와 근무 불가 대상은 경고한다. 기존처럼 초안에서 선택은 가능하나 전체 검증을 통과하지 않으면 확정할 수 없다. 여유 필터는 이동 후 정원이 맞는 코스만 남긴다.
- 코스 없는 직원은 미배정·차량 미배정으로 표시하고 선택하지 못하게 한다. 먼저 기존 코스를 배정해야 한다는 기존 제약은 유지한다. 기본 코스나 새 차량 배정을 자동 생성하지 않는다.
- 선택 창은 열 때의 catalog와 draft를 읽기 전용으로 표시한다. 선택 시에도 같은 draft인지, 조회/저장 오류가 없는지 확인한 뒤 기존 movePassenger만 호출한다. 도중 초안이 바뀌면 적용하지 않고 재확인을 안내한다. 서버 확정본과 충돌한 초안의 확정은 기존 conflict/expectedVersion 검증으로 차단한다.
- 날짜/시간대, 초안 및 원래 시각 제거 동작은 기존 컨트롤러를 사용한다. 검색/필터만으로 저장이나 배정 변경을 하지 않는다.

파일: lib/widgets/reassignment_dialog.dart, lib/screens/admin_schedule_view.dart.

## 전체 확정 변경 요약

확정 창을 열 때 선택 날짜·시간대의 현재 draft, 기존 confirmed, catalog를 함께 고정한다. 기존 확정본 대비 변경 항목을 먼저 보여주고 `전체 일정 N개 코스 보기`에서 원래 검토 내용을 펼칠 수 있다.

| 종류 | 표시 |
|---|---|
| 이용자 배정 | 기존 직원·코스 → 새 직원·코스, 이동 전후 방문 순번 |
| 코스 담당 직원 | 코스별 기존 직원 → 새 직원 |
| 방문 순서 | 남아 있는 이용자의 상대 순서가 바뀐 코스의 이전/변경 목록 |
| 결석·제외 | 처리와 해제를 각각 표시 |
| 차량 | 기존 차량 → 새 차량 |
| 예상 시각 | 방문 시각과 운행 구간의 이전 → 변경, 삭제는 미입력 |
| 첫 확정 | 이전 확정본 없음으로 안내하고 전체 일정은 기본으로 펼침 |
| 변경 없음 | 기존 확정 일정과 변경사항이 없음을 명시 |

재배정·결석으로 이용자가 빠졌다는 이유만으로 남은 이용자의 순서 변경을 중복 보고하지 않는다. 재배정된 이용자의 목적지 방문 순번은 배정 변경에 포함한다. 하나의 재배정으로 배정과 예상 시각 제거가 함께 바뀔 수 있으므로 항목 수는 변경된 직원/이용자 수와 다르다. 버전/확정 Timestamp만 달라진 경우는 일정 내용 변경으로 보고하지 않는다.

첫 확정과 기존 확정본에서 변경 없음은 구분한다. 변경 없음 표시 때문에 새로운 서버 저장 정책을 추가하지 않으며 기존 확정 버튼·검증 규칙을 따른다. 요약은 표시용이며 서버로 전송하거나 검증 근거로 사용하지 않는다.

승인 시 draft와 기준 confirmed가 검토 시점과 같은지 재확인한다. 다른 관리자가 갱신했거나 조회 상태가 바뀌면 저장하지 않고 재검토를 안내한다. 실제 publish와 서버 동시 수정·중복 요청 검증은 기존 구현을 유지한다.

파일: lib/models/schedule_changes.dart(저장 모델이 아닌 순수 비교), lib/widgets/schedule_change_review.dart, lib/screens/schedule_screen.dart.

## 검증 범위

test/schedule_changes_test.dart는 자연 정렬·동명이인 정렬·큰 숫자, 첫 확정/변경 없음, 재배정·상태·차량·시각 변경, 순서 변경, 복귀, 다른 날짜·시간대 비교 차단을 검증한다.

test/admin_usability_test.dart는 실제 직원 행 순서, 검색/복합 필터, 미배정·정원 경고, 오래된 재배정 선택 무효화, 변경 우선 보기/전체 일정 펼치기, 변경 없음, 검토 중 원격 갱신 차단, 320×568 재배정 창을 검증한다. 기존 정원 초과·확정·인증·19시 선택 테스트도 유지한다.

브라우저 검증은 기존 직원 20명·이용자 80명 Emulator 도구를 재사용하며 `OPERATIONS_RUN_LABEL=usability`로 이전 검증 산출물과 분리한다. 검색·필터를 실제 선택하고, 요약 확인 후 Callable 확정과 직원 본인 조회·권한 거부를 확인한다. 원본 37개 Emulator 테스트는 별도의 깨끗한 세션에서 수행한다. 재설계나 새 서버 기능, 실제 서비스 배포는 하지 않는다.

## 2026-11-13 검증 결과

- flutter analyze: 문제 없음.
- flutter test: 89개 모두 통과(기존 74개 + 비교/정렬 8개 + 관리자 UI 7개).
- Auth·Firestore·Functions Emulator 회귀: 37개 모두 통과.
- Emulator용 Web 빌드 성공.
- 실제 Chrome에서 20명/80명 fixture의 자연 정렬, 재배정 검색 및 두 필터, 3항목 변경 요약, v1→v2 확정, 직원 본인 조회 및 타 직원 접근 거부를 확인했다. 원격 Firebase 데이터 API 요청 0건, 미처리 JS 예외 0건이다.
- 최초 브라우저 시도에서 로컬 함수 실행기가 시작하지 못해 저장 실패가 발생했다. 편집 내용이 유지됐으며 서버 코드를 변경하지 않고 Emulator를 새로 시작한 뒤 전체 흐름이 통과했다.
- 실제 Firebase 조회·수정·배포 없음. 임시 Emulator와 테스트 Chrome은 검증 후 종료했다. 원래 운영 규모 snapshot과 기존 baseline은 보존했다.
