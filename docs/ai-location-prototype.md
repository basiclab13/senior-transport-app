# 가상 위치 기반 AI 일정 제안 프로토타입

## 범위와 데이터 호환

Firebase Emulator의 가상 데이터만 사용한다. 실제 Gemini 요청 경로는 유지하며, 새로운 API/지도/서버/컬렉션/규칙이나 자동 확정을 추가하지 않는다. 좌표가 있는 경우 AI에 가상 좌표와 참고 후보를 전달하고, **최종 Gemini 응답**의 변경 전후 거리를 프로그램에서 계산한다. 참고 후보를 AI 응답 대신 몰래 적용하거나 개선을 보장하지 않는다.

기존 `Passenger`는 ID·이름·가상 주소·메모만 가지고 있고, 날짜별 일정은 ID로 이용자를 참조한다. 거리 계산은 서버에서만 수행하므로 Flutter의 이용자 모델과 일정 저장 형식을 변경하지 않는다. 응답 DTO에 선택적 `distanceComparison`을 추가해 기존 검토 대화상자가 표시한다.

`operationsCatalog()` 기본 출력은 그대로 유지한다. 기존 `operations-20x80-v1` 등록 도구는 문서 필드를 정확히 비교하므로 기본 fixture에 좌표를 강제로 추가하면 기존 데이터와 충돌한다. 대신 다음 두 방식을 지원한다.

- 현재 등록된 `operations-20x80-v1`: 80명 fixture의 알려진 ID와 기본 코스를 확인하고 **추천 요청의 메모리 사본**에 고정 가상 좌표를 부여한다. 기존 문서, settings 포인터, 확정 일정, 계정은 수정하지 않으며 초기 데이터를 재등록할 필요도 없다.
- 새 테스트 fixture: `operationsCatalog({withLocations:true})`가 이용자별 선택 필드 `fictionalLocation: {xKm, yKm}`를 생성한다. 기존 CLI의 기본 생성 방식은 바꾸지 않는다.

좌표는 실제 위도·경도가 아닌 km 단위의 가상 평면 값이다. 센터는 `(0,0)`이고, 기본 오전 코스 ID의 자연 정렬 순서로 가상 구역을 배정한 뒤 코스 내 고정 오프셋을 사용한다. 원래 주소를 읽거나 지오코딩하지 않는다. Firestore의 문서 반환 순서가 바뀌어도 좌표는 같다. 기존 기본 코스·직원·차량·방문 순서 자체는 변경하지 않는다.

다른 catalog에 좌표가 없거나 일부 값이 유효하지 않으면 좌표를 추측하지 않는다. 현재 대상 이용자 중 하나라도 좌표가 없으면 거리 비교를 제공하지 않으며, 기존 AI/권한/검증은 유지한다. 좌표 결측을 0km로 표시하지 않는다.

## 계산 방식과 참고 후보

코스 거리는 `센터 → 방문 순서의 모든 이용자 → 센터`의 유클리드 직선 거리 합이다. 각 구간은 `sqrt((x2-x1)^2 + (y2-y1)^2)` km이며 모든 코스의 합을 총 거리로 사용한다. 오전·오후에 같은 센터 왕복 가정을 적용한다. 빈 코스는 0km, 이용자 한 명이면 센터와의 거리 두 배다. 이동·재배정 후에도 같은 좌표와 수식으로 계산한다.

단순 휴리스틱은 다음으로 제한한다.

1. 코스별 최근접 방문 순서를 만들어 기존 순서보다 짧아지는지 비교한다. 가장 큰 개선이 있는 **한 코스**의 순서만 참고 후보에 반영한다.
2. 정원 여유가 있는 다른 코스로 이용자 한 명을 옮길 수 있는지, 각 삽입 위치의 두 코스 거리 합을 비교한다. 아래 추가 이득/업무량 기준을 통과한 후보 중 가장 좋은 이동을 최대 한 번만 선택한다. 참고 후보의 전체 변경 코스는 최대 두 개다.
3. 1m보다 큰 개선이 없으면 원래 순서/배정을 유지한다. 차례가 바뀌었다는 이유만으로 개선이라고 하지 않는다.

### 기존 코스 유지와 업무량 기준

기존 버전은 1m 이상 거리가 줄면 한 명 이동을 선택할 수 있어, 적은 코스의 이용자를 많은 코스로 옮기면서 전체 거리만 약간 줄이는 결과가 나올 수 있었다. 이제 **방문 순서 조정 → 기존 코스 유지 → 필요한 경우에만 이동**을 우선한다. 정상 근무 중인 담당 직원을 불필요하게 바꾸는 AI 응답도 거부한다. 결근/휴무/비활성 담당자의 정상적인 대체는 계속 허용한다.

기준은 `functions/schedule-distance.js`의 `REASSIGNMENT_POLICY` 상수로 분리했다.

- 모든 코스에서 이용자 소속은 그대로 두고 최근접 순서로 검토한 거리 `D_order`를 비교 기준으로 사용한다. 순서만 바꿔 얻을 수 있는 이득을 코스 이동의 이득으로 중복 계산하지 않기 위해서다. 이것도 최적해가 아닌 동일한 단순 휴리스틱의 비교값이다.
- 업무량 지표는 `W = 각 코스 이용자 수의 제곱 합`이다. 같은 시간대 직원당 한 코스이므로 이용자 수 차이가 커지는 변화를 잡는 간단한 대용 지표다. 실제 돌봄 난도나 운행 시간은 반영하지 않는다.
- 불이익은 `C = max(0, W_after - W_before) × 0.25km`다. 3명/5명 → 2명/6명이면 제곱 합이 34 → 40으로 늘어 `C=1.5km`다. 균형이 좋아져도 거리 이득을 부풀리는 보너스는 주지 않는다.
- 실제 AI 거리 `D_AI`에 대해 `G = D_order - D_AI - C`를 계산한다. 코스 간 이동은 `G >= max(1km, D_order × 2%)`일 때만 거리 목적의 이동으로 허용한다. 절대/비율 기준을 **둘 다** 충족해야 한다.
- 이 불이익은 평가용 환산값이다. 기존 화면의 거리/감소량/비율에는 동일한 좌표 계산의 원래 실제 추정 거리만 표시한다.

결석이나 결근이 있다는 사실만으로 모든 이용자 이동을 허용하지 않는다. 결석자 제외나 담당 직원 교체만으로 해결할 수 있으면 이용자의 기존 코스를 유지한다. 제안된 담당 직원 변경을 먼저 반영한 상태에서도 남는 실제 정원 문제 등이 줄어들고, 모든 이동이 해당 문제 코스와 연결되는 경우만 배정 문제 해결 예외로 평가한다. 정상 코스 사이의 별도 이동을 끼워 넣을 수 없다. 기존 요청 전 검증은 여전히 정원 초과 등의 잘못된 초안을 차단하므로, 이번에 그런 입력을 새로 허용하거나 AI 수리 기능을 추가한 것은 아니다. 최종 배정의 정원·근무·누락·중복 검증은 예외 없이 먼저 통과해야 한다.

좌표가 없어 거리 이득을 평가할 수 없으면 임의의 코스 간 이동을 허용하지 않는다. 같은 코스 내 순서 검토와 필요한 담당자 인계는 유지한다. 수동 배정 기능과 기존 최종 확정 규칙은 바꾸지 않는다.

이 기준은 **참고 후보 생성과 최종 Gemini 응답 평가에 모두 적용**한다. Gemini가 참고 후보를 무시하고 기준 미달 이동을 제안하면 `REASSIGNMENT_NOT_JUSTIFIED`로 거부하며 추천안을 몰래 다른 배정으로 바꾸지 않는다. 화면에는 기존 코스를 유지해 다시 요청하거나 방문 순서만 조정하라는 안내를 표시한다. 프롬프트에는 기준 상수와 `orderOnlyTotalKm`를 추가하고, 필요 없는 직원 변경/이용자 이동을 피하도록 명시했다. 새 UI·자동 적용·재시도는 추가하지 않았다.

이번 변경의 필요한 검증: Node 거리/업무 규칙/REST 관련 테스트 40개, 별도 포트 Emulator의 AI 서버 통합 테스트 9개, Flutter AI 관련 테스트 16개 통과 및 `flutter analyze` 오류 없음. 작은 개선/불균형 이동 거부, 두 거리 문턱과 경계값, 충분한 이득 허용, 인계와 이용자 이동의 구분, 정상 20명/80명 소속 유지, 서버에서 프롬프트 위반 거부, 원본 보존을 확인했다. 전체 Flutter/Emulator 재실행 대신 관련 검사만 수행했다. 실제 Gemini 호출·운영 Firebase 변경·배포는 수행하지 않았으며, 사용자 Emulator를 중지하지 않고 별도 포트 테스트 세션만 사용했다.

이는 참고 후보 생성일 뿐 최적화 엔진이 아니다. 직원·차량·결석/제외·예상 시각은 바꾸지 않는다. 근무 가능 직원 선택과 최종 코스/이용자 순서는 실제 Gemini가 제안하며 기존 서버 검증을 통과해야 한다. Gemini가 참고 후보보다 다른 결과를 내더라도 최종 결과로 거리를 다시 계산한다. AI가 유효하지 않거나 실패하면 기존대로 거부하고 원본 초안을 보존한다.

AI 입력에 `locationModel`(방식, 가상 센터, 대상 이용자 ID/좌표, 기존 총 거리, 휴리스틱 후보)을 추가했다. 기존 근무·정원·누락/중복 제한을 유지하고 위치 안내를 추가했다. 출력은 여전히 `baseRouteId`, `staffId`, `passengerIds`뿐이다. AI는 차량·좌표·시각·출처·결석 상태나 거리 비교 값을 출력할 수 없다. 모델·제한 시간·API 키 관리 방식은 바꾸지 않는다. 입력/좌표/원본 AI 응답을 진단 로그에 출력하지 않는다.

## 검토 화면과 설명의 일관성

기존 AI 검토 대화상자에 다음만 추가한다.

- 변경 전/후 추정 총 거리(km)
- 감소 또는 증가량과 기존 거리 대비 비율
- 동일/개선 없음, 좌표 없음 상태
- 가상 평면·센터 왕복 직선 거리이며 실제 도로/교통/운행 시간이 아니라는 설명

1m 이내 차이는 동일하게 취급한다. 기존 거리가 0이면 증가 비율을 계산하지 않고 이를 명시한다. 아주 작은 비율은 0.00% 대신 `0.01% 미만`으로 표시한다. 동일 배정은 기존처럼 변경 없음/적용 비활성 상태를 유지한다. 직원 결근 대체처럼 거리 개선이 없어도 필요한 변경은 사실대로 표시하고 관리자가 판단하도록 한다. 거리 감소만으로 업무 검증이나 예상 시각 검토를 면제하지 않는다.

AI가 자유문장으로 주장한 "99% 단축" 등을 검증 없이 표시하지 않는다. 위치 비교가 가능한 응답에서는 원본 AI 이유 대신 프로그램에서 확인한 감소/증가/개선 없음 설명을 반환하고 제목을 `계산으로 확인한 추천 설명`으로 표시한다. 실제 변경 내용은 기존 전후 비교 요약으로 확인한다. 위치 비교가 없는 기존 응답은 기존 AI 이유 표시를 유지한다.

관리자 승인 → 로컬 초안 일괄 적용 → 영향 코스 B-2 시각 재검토 → B-1 계산 또는 기존 시각 유지 → 기존 전체 확정/직원 조회 흐름을 유지한다. 자동 재계산·자동 적용·자동 확정은 없다. 근무 가능 직원 부족 등의 기존 불가능 조건도 그대로 차단한다.

## 빠른 시연

기존 20명/80명 Emulator fixture가 등록되어 있다면 데이터 작업 없이 변경된 Functions 코드가 반영됐는지 확인한다. 실행 중인 Emulator를 데이터를 보존하지 않고 종료·초기화하지 않는다. Flutter는 아래처럼 Emulator 빌드 옵션으로 실행한다.

```powershell
flutter run -d chrome --dart-define=USE_FIREBASE_EMULATORS=true
```

Gemini Secret/모델 설정과 가상 계정 준비는 [기존 MVP 문서](ai-schedule-mvp.md)를 따른다. 이미 준비한 키와 모델을 그대로 사용한다.

1. 관리자 로그인 → 오전 일정 선택 → `AI 일정 제안` 요청.
2. 위치를 고려한 제안과 프로그램 계산의 전후 거리/감소량/비율을 확인한다. 실제 Gemini가 변경 없음이나 증가한 제안을 내면 해당 결과를 그대로 보여준다. 개선안이 반드시 나와야 한다고 거짓 표시하지 않는다.
3. 변경이 유효하고 원하면 승인해 초안에 적용한다. 바뀐 방문 순서에 기존 수동 시각이 보존되므로 B-2에서 시각을 검토한다. B-1을 쓰는 경우 기존 운행 구간 안의 첫 시각과 간격을 설정하고 수동 시각 변경 확인을 거친다.
4. 기존 전체 변경 검토·확정을 진행하고 담당 직원 계정에서 확정본을 확인한다.

참고: 80명 모두 참석하는 기본 오전 가상 시나리오의 최신 계산 예는 기존 약 276.318km, 코스 내 순서만 바꾼 참고 후보 약 274.534km이며 이용자 코스 이동은 0명이다. 이전 거리 우선 버전의 약 272.907km 후보보다 거리 이득이 작더라도 배정의 안정성을 우선한 결과다. 이는 고정 fixture에서의 **프로그램 참고 계산**이며 실제 Gemini 응답이나 실제 센터 운행 결과가 아니다. 결석·제외·기존 초안 변경에 따라 값은 달라진다. 금요일 예비 직원 휴무와 결근 직원 조합으로 가용 인원이 부족한 경우는 위치 문제와 별개다.

## 변경 파일과 검증

- `functions/schedule-distance.js`: 가상 좌표 생성, 동일 기준 거리 계산, 제한된 휴리스틱, 계산으로 확인한 설명.
- `tools/operations_fixture.cjs`: 기본 출력 보존, 선택적 좌표 fixture 생성.
- `functions/suggestion-service.js`: 읽기 전용 좌표 사본과 위치 입력, 검증 후 거리 비교/사실 기반 설명.
- `functions/gemini-schedule.js`: 기존 업무 규칙에 위치 기반 지침 추가. 실제 Gemini 호출 경로 유지.
- `lib/models/ai_schedule_suggestion.dart`: 선택적 거리 비교 DTO와 표시용 값 검증.
- `lib/widgets/ai_schedule_suggestion_dialog.dart`: 기존 대화상자에 비교와 한계 표시.

## 한계

실제 위치·도로망·일방통행·교통·차량 출발지·운행 시간·이용자 사정은 반영하지 않는다. 센터 왕복 총합은 배차 균형이나 최대 운행 시간을 최적화하지 않는다. 휴리스틱은 제한된 참고 후보로 전체 최적해를 보장하지 않으며, Gemini도 이를 따르거나 개선할 의무가 없고 업무 규칙을 어길 수 있다. 필수 검증과 관리자 판단을 계속 사용한다. 예상 방문 시각은 거리에서 자동 계산하지 않는다.
