# 공통 날짜·오전/오후 선택

관리자와 직원은 같은 ScheduleScreen과 ScheduleController를 사용한다. ScheduleSelectionPolicy를 추가해 기기 시간대와 무관하게 현재 instant를 한국 시간(Asia/Seoul, 현대 운영 날짜의 UTC+09:00)으로 해석한다. 외부 시간대 패키지나 Firestore 설정은 추가하지 않았다.

| 한국 시간 | 최초 진입 / 현재 일정 버튼의 선택 |
|---|---|
| 00:00 이상 ~ 09:30 미만 | 오늘 오전 |
| 09:30 이상 ~ 19:00 미만 | 오늘 오후 |
| 19:00 이상 ~ 다음 자정 미만 | 내일 오전 |

이 기준은 일정 선택 정책이며 실제 출발·방문·종료 시각을 자동 설정하지 않는다. 오후 준비·출발이 17시보다 앞설 수 있음을 반영해 오전 종료부터 오후 일정을 선택한다. 오후 송영이 보통 18:30 이전에 종료되는 운영 기준에 맞춰 2026-11-13부터 저녁 전환 기준을 19:00으로 변경했다.

## 동작

- 컨트롤러 생성 시 한 번 날짜와 시간대를 함께 선택하고, 그 일정만 조회한다. 새로 인증 화면이 만들어져 컨트롤러가 다시 생성될 때에는 당시 시각을 사용한다.
- 달력, 전날/다음날, 오전/오후 수동 선택은 유지한다. 자동 변경 타이머나 앱 복귀 시 재선택을 넣지 않았다. 수동 선택뿐 아니라 최초 선택도 사용자가 바꾸기 전까지 고정된다. 서버 새로고침은 날짜·시간대를 바꾸지 않는다.
- `현재 일정`은 누른 순간의 정책을 한 번 적용한다. 날짜와 시간대를 함께 바꿔 중간 날짜/시간대의 불필요한 조회를 만들지 않는다. 저장 중에는 선택을 바꾸지 않으며 같은 일정을 다시 선택해도 조회를 재시작하거나 초안을 초기화하지 않는다.
- 다른 일정으로 이동해도 기존 날짜·시간대별 초안 보존 방식을 유지한다. 현재 일정 버튼은 초안 폐기나 일정 확정 버튼이 아니다.
- 날짜 선택 버튼은 `오늘 · 11월 12일 (목) · 오후`, `내일 · 11월 13일 (금) · 오전`처럼 표시한다. 다른 날짜는 `2026년 11월 16일 (월) · 오후`처럼 연도까지 표시한다. 상대 날짜는 한국의 실제 오늘과 비교하며 19시 이후에도 아직 내일인 선택 날짜를 오늘이라고 표시하지 않는다.
- 전체 직원 확정 대화상자의 제목과 `확정 대상`에 선택한 스냅샷의 YYYY-MM-DD, 요일, 오전/오후를 명시한다. 대화상자를 열 때의 실제 선택을 사용하며 당시 자동 추천 일정으로 바꾸지 않는다.

## 기준값과 변경 파일

- `lib/services/schedule_selection_policy.dart`: 오후 선택 시작 `afternoonFromMinute=570`, 내일 오전 선택 시작 `nextMorningFromMinute=1140`, 서울 UTC 오프셋과 날짜/요일 표시. 향후 운영 기준 변경은 이 기본값이나 컨트롤러에 전달하는 정책 객체로 조정한다.
- `lib/services/schedule_controller.dart`: 두 생성자의 공통 정책 적용, 원자적 날짜·시간대 전환, 현재 일정 복귀, 표시용 라벨. 테스트용 clock을 주입할 수 있다. 로컬 테스트/프리뷰의 명시적 initialDate는 기존처럼 지정 날짜 오전에서 시작한다. 앱의 실제 원격 컨트롤러는 자동 정책을 사용한다.
- `lib/screens/schedule_screen.dart`: 관리자·직원 공통 날짜 표시 및 현재 일정 버튼, 확정 대상 표시.
- `test/schedule_selection_test.dart`: 경계 시각 직전/정각, 자정, 월말·연말·윤년, 다른 UTC 오프셋 입력, 기준값 변경, 수동 선택/초안 유지, 서버 재조회 시 선택 유지, 한 번의 구독 전환, 저장 중 차단, 양 역할과 320×568 화면, 미래 날짜 확정 대상.
- 기존 테스트에는 고정 clock을 전달해 실제 실행 시각에 따라 오전/오후가 달라지지 않도록 한다. 테스트 가상 데이터와 실제 Firebase 조회 데이터를 섞지 않는다.

Auth·Firestore 저장 형식·confirmSchedule·Security Rules·기존 검증·확정 절차는 변경하지 않는다. 선택 동작은 조회 대상을 바꿀 뿐 Firestore에 일정을 쓰지 않는다. 실제 Firebase 데이터 수정이나 배포는 수행하지 않는다.
